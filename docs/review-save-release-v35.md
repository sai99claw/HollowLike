# 檢討修正：永久資料與發布檢查

永久資料保留原本 `pigeon_tower_v1.json` 格式與路徑。每次儲存先寫入 `.tmp`、關閉並驗證，再替換主檔；有效的舊主檔保存在 `.bak`。載入時先驗證主要欄位與型別，主檔損壞或空物件時嘗試備份並顯示恢復提示。損壞主檔不會覆蓋好的備份。若主檔與備份都損壞，保留原檔並暫停該路徑寫入，提示保留檔案以便修復。

這是同一裝置／瀏覽器的本機備份，不是跨裝置雲端存檔；清除網站資料也會清除本機備份。沒有改動冒險死亡、倉庫存放與金幣規則。

Web 輸出在獨立暫存目錄完成匯出、實際 PCK 回歸、拆檔及校驗後，先計算每檔與總體積，再建立完整候選目錄取代 `dist`。失敗的匯出不再先刪除上一個成功的 `dist/client`。候選目錄只含此次產物，舊 chunk、暫存檔、測試及文件不會從舊輸出混入。最終 Worker 包含在完整 256 MiB 預算驗證中，餘額小於 8 MiB 時提示下次新增素材需注意。

沒有移除任何 runtime 素材、改變 hosting identity 或憑證。256 MiB 是發布平台限制，預檢不會壓縮或降低貼圖品質以掩蓋超限。

驗證：`test_save_recovery_v35.gd` 覆蓋正常輪替、損壞主檔、空 JSON、無效新資料、兩檔損壞保留；`test_release_budget_v35.py` 覆蓋單檔／總量邊界與 Worker 計算。完整 Web 匯出由整合發布流程執行。

發布順序：各修正分支先提交 → 整合回歸 → 先保存／推送可恢復的原始碼 checkpoint → 建置及打包 → 保存版本 → 發布。不要讓未提交的工作成為唯一副本。必要時只保存原始碼而不發布未驗證的遊戲。
